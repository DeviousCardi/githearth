
## `verify-m4.py` S1 — exact command and result

The full harness runs thirteen scenarios (including a rebuild of the previous
release for the upgrade drill and Docker disk-full drills); the brief allows the
S1 path, so I drove only `M4Harness.s1_install_from_runbook` from the real
module. Driver (kept in `ops-artifacts/run-s1.py`):

```python
spec = importlib.util.spec_from_file_location("verify_m4", "<repo>/scripts/verify-m4.py")
mod = importlib.util.module_from_spec(spec); spec.loader.exec_module(mod)
h = mod.M4Harness(REPORT)
try:
    h.start_db()
    h.scenario("s1_install_from_runbook", h.s1_install_from_runbook)
finally:
    h.cleanup()
h.write_report()
```

Command and output:

```

$ python3 …/ops-artifacts/run-s1.py
PASS: s1_install_from_runbook
[{"name": "s1_install_from_runbook", "result": "PASS", "wall_seconds": 0.847}]
exit 0
```

Report metadata: `source_revision cd7946bf714393fb44a294248906af0e63994ff2`,
`git_version 2.50.1`, macOS arm64. It was run twice; both runs passed.

This is the assertion that changed in `ebfe479`:

- `scripts/verify-m4.py:323` snapshots the key, then
- `:333-336` requires the rerun to **exit 0** and the bytes to be **unchanged**.

The old harness asserted the opposite (`if p.returncode == 0: raise …`). The
binary has been idempotent since `7e1ded3`: `crates/githearth-server/src/ssh.rs:58-63`
catches `AlreadyExists`, logs `SSH host key already exists; keeping it`, and
returns `Ok(())`; `crates/githearth-server/src/main.rs:96-99` runs it before any
database connection. The harness was stale, not the product.

## Observations (not defects)

1. **A one-byte flip in the custom-format dump is not rejected by
   `pg_restore`.** The byte landed in a region PostgreSQL does not validate on
   restore; `pg_restore --list` also accepted it, and the restored rows were
   intact. The documented control is the `SHA256SUMS` manifest, and that did
   detect the change (R4). A *truncated* dump is rejected by `pg_restore` (R5).
   This is PostgreSQL dump-format behaviour, not a GitHearth defect; keep the
   manifest step.
2. **`doctor` treats a missing storage root as a warning, not a failure**
   (`warn storage: /nonexistent does not exist; will be created by serve`, exit
   0). This matches `serve` creating the directory and the documented
   "warnings are allowed" exit rule; a genuinely invalid config (over-long
   path) exits 1.
3. **SSH authentication fails closed when PostgreSQL is down.** During the
   readiness drill an SSH clone attempted while postgres was stopped failed with
   `Could not read from remote repository`; it succeeded immediately after the
   database returned. Expected: SSH authentication reads `ssh_keys` from the DB.

## Notes and limits

- The second project's data lived entirely in `ghm4r4_*` volumes; the primary's
  volumes were never touched. `docker compose -p ghm4r4 down` initially left
  `ghm4r4_default` because my temporary restore container was still attached;
  after removing that helper, `down` removed the network. That is Docker's
  in-use rule, not a Compose-file defect.
- The restore drill restored into a fresh database and a fresh storage root and
  started a second server on `:18081`; it was removed after R8/R9. The backup
  used for it was taken before any corruption, so R10 also proves the backup is
  a working recovery point.
- The three re-run setup failures: (a) strict-check SSH clone before
  `ssh-keyscan` populated `known_hosts`; (b) the same clone racing the
  intentional postgres stop in a parallel tool call; (c) `chmod u+w` needed on a
  read-only loose object before corrupting it. Each passed on the re-run.
- The repository working tree remained clean; only `target/` build outputs were
  refreshed to run the harness.
- Primary confirmation after cleanup: `ready=200`, `t07` login 200, both primary
  containers still healthy and not restarted.
