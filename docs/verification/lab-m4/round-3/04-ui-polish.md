### Observation — transient 503 on PR pages under concurrent Git load (not counted as a #158 failure)

- Severity: minor (availability sharp edge, pre-existing/unrelated to the #158 changes)
- Repro: while several queue merges and a push to `main` were in flight, `GET …/pulls/14` and `…/pulls/15` returned the 503 “Unavailable” page three times each over ~3 s (logged as status 503 in 3 ms). The same requests returned 200 immediately afterwards, and the JSON read API returned 200 throughout.
- Expected: a readable PR page, or a wait rather than an instant 503.
- Actual: `browse::git_compare` returns 503 “git requests busy” when its Git permit cannot be acquired, and `pulls_ui::api_error` maps every unmapped error to the generic 503 page (`crates/githearth-server/src/browse.rs:83`, `crates/githearth-server/src/pulls_ui.rs:191-215`). This is a saturation window while the merge worker or a large push holds the permit, not a recurrence of the round-2 changed-PR blocker (the API read was 200 and the pages recovered).
- Evidence: three consecutive 503s for PR 14/15, then 200; `docker compose logs` shows `GET …/pulls/{number}` status 503 elapsed_ms 3 while the API read and other PR pages were 200. Re-run after the merges finished passed.

## Notes

- **Navigation badge:** the unread count is rendered on `/notifications` (`notifications_ui.rs:260`) but not in the nav (`ui.rs:156`). Issue #158 says “no unread badge/count in the nav **or** page”; the page badge satisfies the issue, so this is recorded as a note, not a failure. The count is exact over all unread rows while the list is capped at 50 (verified 55 vs 50).
- **`ff_only` notice:** the UI maps the 409 to the generic “This pull request cannot be merged right now.” The API body is specific (“target is not an ancestor of the source”). The method form remains on the page after the refusal so the user can choose merge/squash; the form is hidden when mergeability blocks the selected method, when the PR is closed/merged, or while an intent is live.
- **Tag role echo:** an invalid role (`superuser`) cannot be echoed into the `<select>` because it is not an option; the pattern and checkboxes are preserved and the message explains the problem. This is expected browser-form behaviour, not lost input for a valid choice.
- **Cancel scope:** the cancel control is only rendered for `in_queue` intents (merge-queue-protected branches, `pulls_ui.rs:1164-1179`). Direct merge intents never show a queue position, so no control is expected there.
- **Source references:** comment ids `pulls_ui.rs:1124` and `pulls_ui.rs:1248`; wrapping/table/checkbox CSS `ui.rs:178-185`; unread count `notifications_ui.rs:176-260`; tag form re-render `tag_protection_ui.rs:273-320`; ff-only pre-check `merge_intents.rs:613-628` and `mergeability.rs:165-206`; cancel form/route `pulls_ui.rs:59-64, 1164-1179, 1857-1885`; merge-form guard `pulls_ui.rs:1095-1116`.
- Fixtures added: `lab04/r3-ui`, issues #69–#71, PRs #1–#90, tag rule `r3-ok-*`, branch rules `qtarget` and `gmain1..8`, grants for `bob` (write) and `erin` (read). No other org/repo/test data was modified.
