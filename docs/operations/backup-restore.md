# Backup and restore

`githearth-server backup` writes one encrypted archive; `githearth-server
restore` proves it on a fresh host before it publishes anything. A backup is
only proven by restoring it. The M4 manual dump/tar procedure did not stop
writes and is replaced by these commands (see the correction in
[m4-qualification.md](../verification/m4-qualification.md)).

## Which path `backup` takes

`backup` probes the storage filesystem for copy-on-write cloning before it
writes anything. On a filesystem that supports it, the **online** path is used:
the command briefly gates the running server, drains the writers already in
flight, records a PostgreSQL snapshot position and one journal position per
repository, clones the storage root, verifies every journaled client-visible
ref, and releases the gate. The database dump, storage tar, encryption and
archive verification then run while writers continue. There is no operator
maintenance window.

On a filesystem without copy-on-write (or with `backup_snapshot_mode =
"fence"`), `backup` falls back to the M4.1 fence. It refuses to run unless it
has proved that **no writer can acknowledge a commit**. It names the path it
used in its output and records it in `manifest.fence` and `manifest.snapshot`:

- `online-snapshot` — the filesystem probe succeeded; the running server was
  briefly gated for the position and clone and released;
- `not-running` — both the HTTP bind and, when SSH is enabled, the SSH bind
  refuse a connection; or
- `maintenance` — the running server reports `drained` with zero writes in
  flight over the authenticated, loopback-only maintenance control endpoint.

A running server is refused on the fallback path unless it is drained. The
fence path proves the fence again after the database dump, immediately before
the storage snapshot, so stopping maintenance mode during the dump cannot
produce a racing snapshot.

On the online path, a write that started before the brief gate is in the
restore; a write that starts while the clone is taken is refused with `503`
before acknowledgement. Writers continue during the long dump, tar and
encryption steps, which are after the recorded position by construction: a
write acknowledged after the gate is released is in neither the storage
snapshot nor the database dump (the dump is pinned to the exported snapshot),
so it is not in the restore and nothing claimed it would be.

`backup` releases the gate on every failure path — a staging directory that
cannot be created is made before the gate starts; a drain timeout, a control
request failure, a panic and an interrupt all stop the gate before the command
exits. A failed `backup` never leaves the server refusing writes. If an
interrupted or killed run did leave it fenced, `githearth-server maintenance
stop` releases it.

Immediately before `pg_dump`, `backup` re-runs the same start-up secret check
the command ran first (every wrapped data key opens, no plaintext audit IP key
remains), so a mixed-version writer that admits a plaintext audit key during
the dump window cannot put it in the archive.

The fence covers every path that can acknowledge a write:

- the JSON API and browser handlers, through middleware that refuses a write
  with `503` while fenced and counts an admitted write until it finishes;
- Git Smart HTTP: fetches (`git-upload-pack`, reads) continue, while
  `receive-pack` takes a permit that is held until the journal replay has
  committed — not merely until the response headers are written;
- Git over SSH, which takes the same permit before running a write command;
- the background writers that touch the storage tree: the reconciler's
  mutating pass, the merge worker and the housekeeping job handler. Each takes
  the permit for its whole unit of work, so `maintenance start` waits for one it
  interrupted and the worker pauses while the fence is up.

`maintenance start` waits up to `maintenance_drain_timeout_seconds` (default
300) and exits non-zero with the number of writes still in flight if they do
not finish. `maintenance status` shows the phase and count. The control endpoint is
cryptographically authenticated and answers only a loopback client; with an
explicit non-loopback `bind`, stop the server and use the `not-running` fence
instead.

## What the archive holds

One archive contains:

- `database.dump` — a PostgreSQL custom-format dump;
- `storage.tar` — the storage root, excluding `run/` (sockets, the control
  token and maintenance state), `tmp/` (scratch directories) and `hooks/`
  (regenerated by `serve`);
- `config.toml` — the effective configuration, including `database_url`; it
  holds credentials, which is why the archive is encrypted;
- `ssh_host_key` — the private host key when SSH is enabled;
- `manifest.json` — a SHA-256 checksum for each part, one journal position per
  repository, the PostgreSQL position and exported snapshot id, the fence kind
  and detail, the snapshot mode and mechanism, the excluded paths, and the
  encryption record. It also lists each per-account and per-organization data
  key by id, owner, algorithm and wrap method (and whether it was shredded);
  it never carries an owner key or a wrapped key. The key files themselves live
  in operator custody outside the archive.

`manifest.postgres.dump_lsn` is the WAL position read inside the exported
repeatable-read transaction, and `manifest.postgres.exported_snapshot` names
the snapshot `pg_dump --snapshot` used, so the dump is exactly the recorded
position. Database-to-storage consistency is additionally proved by the
per-repository journal positions in the manifest.

`manifest.snapshot` records `mode` (`copy-on-write` or `maintenance-fence`),
the mechanism (`clonefile`, `reflink` or `whole-root-tar`) and
`refs_verified`. `manifest.repositories[].refs_digest` is a SHA-256 digest of
the whole client-visible ref set read from the live repository at the recorded
position, before the snapshot. `backup` requires the clone, the archive it just
wrote and the staged tree before `restore` publishes it to reproduce that
digest, and separately replays each journal to its recorded position. A ref
that disappears from the snapshot therefore refuses the backup even when no
journal record names it (a pre-0005 ref, an import or a fork). An archive
written before `refs_digest` existed is verified against the journal only.

The archive is encrypted with AES-256-GCM under an Argon2id-derived key
(64 MiB of memory, 3 iterations, a fresh salt and nonce per archive). The
manifest records the key id, `AES-256-GCM`, the Argon2id parameters and the
`argon2id-symmetric` wrap method. It never contains the key. Losing the key
means the archive cannot be decrypted; there is no recovery path by design.

`backup` re-reads the archive it just wrote, decrypts it, verifies every part,
extracts the storage snapshot and runs the same `Storage::check` that `restore`
runs. Only then does it publish the output path. A backup that cannot be
restored is not left behind.

## Take a backup

With a copy-on-write filesystem, no maintenance step is needed:

```sh
# Encrypted backup. The key is read from a file or stdin, never an argument.
githearth-server --config /etc/githearth/config.toml backup \
  --output /srv/backups/githearth-20261115.ghbackup \
  --key-file /etc/githearth/backup.key
```

The command prints:

```
fence: online-snapshot (server at 127.0.0.1:8080 drained with 0 writes in flight and was gated only for the recorded position and the copy-on-write snapshot)
snapshot: copy-on-write (probed on the storage filesystem)
backup written: /srv/backups/githearth-20261115.ghbackup (… bytes, N repositories, advisory dump LSN …, key sha256:…)
manifest: key id sha256:…, AES-256-GCM, Argon2id wrap; the key is not in the archive
fence used: online-snapshot (…)
storage snapshot: copy-on-write
```

On a filesystem without copy-on-write, stop accepting writes and wait until
in-flight pushes, API writes and background work (merge, reconcile and
housekeeping) finish:

```sh
githearth-server --config /etc/githearth/config.toml maintenance start
githearth-server --config /etc/githearth/config.toml maintenance status

githearth-server --config /etc/githearth/config.toml backup \
  --output /srv/backups/githearth-20261115.ghbackup \
  --key-file /etc/githearth/backup.key

githearth-server --config /etc/githearth/config.toml maintenance stop
```

The fallback prints `fence: maintenance`, `snapshot: maintenance fence`,
`fence used: maintenance` and `storage snapshot: maintenance-fence`. With the
server stopped it prints `fence: not-running` and names both refused listeners.

`--key-file` reads a file; `--key-stdin` reads the piped key (stdin must not be
a terminal, so a key is never echoed). Without either flag, `backup_key_file`
from the configuration is used. There is deliberately no key argument.

Configuration keys:

| TOML key | Environment | Default | Meaning |
| --- | --- | --- | --- |
| `backup_directory` | `GITHEARTH_BACKUP_DIRECTORY` | `backups` | Directory used when `--output` is omitted |
| `backup_key_file` | `GITHEARTH_BACKUP_KEY_FILE` | empty | Key read when neither `--key-file` nor `--key-stdin` is given |
| `backup_snapshot_mode` | `GITHEARTH_BACKUP_SNAPSHOT_MODE` | `auto` | `auto` probes for copy-on-write; `fence` keeps the maintenance-window path |
| `maintenance_drain_timeout_seconds` | `GITHEARTH_MAINTENANCE_DRAIN_TIMEOUT_SECONDS` | `300` | How long `maintenance start` (and the online gate) waits for in-flight writes |

## Restore on a fresh host

`restore` needs no running server: it reads the archive, creates a fresh
database and publishes storage, configuration and the host key directly. Put
the destination database URL in the environment; it is never an argument.

```sh
export GITHEARTH_DATABASE_URL='postgres://githearth:PASSWORD@127.0.0.1:5432/githearth'

githearth-server --config /etc/githearth/config.toml restore \
  --archive /srv/backups/githearth-20261115.ghbackup \
  --key-file /etc/githearth/backup.key \
  --storage-root /var/lib/githearth/repositories \
  --ssh-host-key-path /etc/githearth/ssh_host_key
```

The destination database must **not exist**; `restore` creates it and drops it
again if any later step fails. It also refuses an existing configuration file,
an existing host key and a non-empty storage root, so it cannot overwrite a
live installation. `--storage-root` and `--ssh-host-key-path` override the
paths recorded in the archive; the published configuration is rewritten to
name the destination database, storage root and host key.

Before publishing anything, `restore`:

1. verifies every manifest checksum and that the manifest key id matches the
   archive header;
2. restores the database into the new name;
3. extracts and checks the storage snapshot;
4. verifies every repository's journal position and its client-visible refs,
   and that the metadata does not run past it, and that the database and
   storage agree.

A failure removes whatever the command created (storage, configuration, host
key and database) and leaves the destination as it found it.

The four archive-key refusals are distinct:

| Condition | Message starts |
| --- | --- |
| wrong key | `wrong backup key for this archive (archive key id …)` |
| missing key | `no backup key supplied; pass --key-file or --key-stdin` |
| corrupted archive | `backup archive is corrupt: …` |
| incomplete archive | `backup archive is incomplete: expected … bytes, found …` |

The installation key is separate from the archive key and each failure mode is
also distinct:

| Condition | Message contains |
| --- | --- |
| installation key file absent | `installation key file … is missing` |
| key file readable by group/others | `group or others could read it` |
| wrong key | `wrong installation key: the archive records key id …, but the supplied key is …` |
| key id not in the archive | the same `wrong installation key` refusal |
| a wrapped data key cannot be opened | `the restored database's secrets do not match the installation key` |
| a per-owner data key is missing without a tombstone | `is missing from …; restore the operator-custody key, or record the deletion` |
| a per-owner data key was shredded | `owner data key(s) that were shredded: …`; restore refuses by default and names the keys |
| the same archive with `--accept-shredded` | restore succeeds, prints the shredded-key count, and its secrets stay unreadable by design |

A shredded key is a completed deletion, not a lost key, so `restore` will not
silently publish a database whose secrets are unreadable. Naming the keys is the
signal that the archive covers a period in which an account or organization was
deleted; `--accept-shredded` is the operator saying that outcome is intended.

A pre-key archive (one taken before per-account keys existed) has no
`data_keys`; it restores as plaintext-shaped secrets under the installation key
and **cannot be shredded at all**, because the key that would be destroyed did
not exist when the backup was taken. Retention is the only control for that
archive; the same is true of the plaintext profile columns in any older backup.
Keep `data_key_directory` with the installation key off-host; a tombstone in
that directory is what distinguishes a completed shred from a lost key.

None of these publishes storage or configuration, and none leaves a database
behind. `restore` never starts a server; `serve` repeats the same check at
start-up and refuses to listen with unreadable secrets.

After a restore, start `serve` with the published configuration and do a
representative clone. The reconciler replays any journal records newer than the
metadata position; repositories created after the backup appear under
`orphans/`.

## Off-host copy

A backup on the same host does not help when the host fails. Because the
archive is one authenticated, encrypted file, the off-host unit is that file
plus, **separately**, its key:

1. Copy the archive to the backup host and compare its SHA-256 on both ends:

   ```sh
   sha256sum githearth-20261115.ghbackup
   scp -i /etc/githearth/backup-key \
     githearth-20261115.ghbackup \
     githearth-backup@backuphost.example.com:/srv/backups/githearth/
   ssh -i /etc/githearth/backup-key githearth-backup@backuphost.example.com \
     sha256sum /srv/backups/githearth/githearth-20261115.ghbackup
   ```

2. Keep the key on a different medium and a different access path. A stolen
   archive must not also yield its key. Do not store the key beside the
   archive or in the same backup account. Do the same for
   `data_key_directory`: it holds the per-account and per-organization keys
   that an archive deliberately omits. Without it, an archive's secrets cannot
   be read. A shred is only as strong as the custody copies you discard: keep
   only the current directory, or a copy that has had every shredded key
   removed; never restore a custody copy that predates a deletion, because an
   old copy has neither the tombstone nor the removal and would make the older
   archive readable again. After a shred, remove the key from every retained
   copy, and verify a restored archive against the **current** directory.

3. Fetch the archive back to the new primary host, check its SHA-256 again, and
   run `restore` as above. A remote copy is not a backup until it has been
   restored at least once.

The archive contains the configuration file (including the database URL and
its password) and the SSH host key, so its key is as sensitive as those files.
`restore` decrypts them; nothing else on the backup host needs the key.

### Retention

Keep N most-recent generations (for example `N=7` for a daily backup) and prune
older archives. Retain the key separately for every archive still kept. Backup
retention also bounds IP retention: raw IPs pruned from the live database and
old audit keys still exist inside older encrypted archives — see
[audit-retention.md](audit-retention.md).

## What this does not cover

- **Online backup.** M4.1 still needs a maintenance window (or a stopped
  server). M4.2 adds the single-node online mode with a filesystem snapshot.
- **Secrets held outside the archive.** From M4.2 stored secret columns are
  encrypted under an installation key that is not in the archive. In M4.1 the
  configuration and host key are in the archive; any out-of-band key material
  you keep must still be backed up separately.
- **Rotated/archived journals** (`journal.<first>`): the storage check reads the
  live `journal` file. Search indexes are rebuilt after restore.
- **The advisory PostgreSQL LSN.** It is recorded, not compared.
- **The drill harnesses — demonstrated on macOS.** On 2026-11-16, with Docker
  Desktop 4.97.0 (Engine 29.9.2) on macOS 26.6 arm64, both harnesses ran to
  completion against the release builds:
  - `scripts/verify-offhost-backup.py` — **5/5 scenarios**. It exercised the
    `maintenance` and `not-running` fences (printed and recorded in the
    manifest), the encrypted archive and its manifest (key id, AES-256-GCM,
    Argon2id with 64 MiB / 3 iterations, and no key), the four distinct restore
    refusals, the off-host copy (one file, SHA-256 equal on both ends) and the
    disaster restore. The 2026-11-15 attempt stopped at `backup host sshd not
    reachable within 30 s`; the harness now publishes the backup host's sshd
    port on the host loopback when the platform is Darwin and keeps
    `--network host` on Linux. That is harness plumbing only — no assertion
    changed. See [offhost-backup.md](../verification/offhost-backup.md).
  - `scripts/verify-m4.py` — **13/13 scenarios**, including
    `s4_backup_restore` and `s5_upgrade_drill`.
  - A very long `$TMPDIR` breaks a legitimate step: the restored storage root
    would put the hook socket over the product's 107-byte Unix limit, and
    `restore` refuses it correctly. Use a short temp root (`/tmp` on Linux, and
    the harness moves itself under `/tmp` on Darwin).
  - Both harnesses work in a temporary directory. On this machine a shared
    `/tmp` was being pruned by another session mid-run, which produced spurious
    failures (a `cargo` build losing its object files, then `SSH listening log
    line not seen within 30s`); the passing runs used a private temp root. This
    is an environment hazard, not a product defect.

  U20's clause — both harnesses use `backup`/`restore` and pass — is met.

The manual `pg_dump` / `tar` / `SHA256SUMS` / `rsync` procedure in older
releases did not fence writers. Do not combine it with these commands; use
`backup` and `restore`.
